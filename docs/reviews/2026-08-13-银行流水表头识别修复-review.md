# 验收审查报告：银行流水表头识别修复

- 日期：2026-08-13
- 审查阶段：需求优先工作流 · 阶段 5（验收审查）
- 审查对象：本次对 `core/detection.py` 与 `core/merging.py` 的修改

## 一、审查范围

本次修复要解决的真实问题：

1. 银行账户明细查询结果（2024 / 2025 / 2026 三个文件）合并后，表头错位、数据大量丢失。
2. 根因有两处：
   - 表头识别按「候选段落评分最高」挑选表头所在段，数据较多、被空行切成多段时，会误把某段里的真实交易记录当成表头。
   - 数据采集遇到「连续空行」即提前结束，导致银行流水中间的分隔空行把数据截断。

本次审查覆盖：

- 正确性：表头识别、数据采集是否修对。
- 数据损失风险：是否会漏采、错采数据。
- 兼容性：对既有测试和其他用法的影响。
- 可维护性 / 过度工程：是否引入死代码、冗余逻辑。
- 测试：是否真正验证行为，正常 / 边界 / 错误路径是否齐全。

## 二、发现的问题与修复

### 问题 1（严重，已修复）：表头按「段落评分」选错

原逻辑先按空行把文件切成多个候选段，再选段落评分最高的一段当表头所在段。
2024 文件被切成多段后，选中了「数据密集段」（评分 0.538），而真正表头所在的段落评分只有 0.244，导致表头被识别成一条交易记录。

修复：改为**整表遍历所有行**，选「表头打分」最高的那一行作为表头，不再依赖段落评分。真表头行（含「交易日期、交易时间、对方账号」等关键词）打分稳定高于数据行。

### 问题 2（严重，已修复）：数据采集遇连续空行提前停止

原逻辑 `max_consecutive_empty = 3`，连续 3 个空行即判定表格结束。银行流水数据中间大量空行分隔，导致 2024 只采到 4 行（应 200+ 行）。

修复：空行直接跳过、不终止采集；仅当遇到连续多个「非空但非数据」的行时才终止。`detection.py` 主路径与 `merging.py` 模板复用路径两处同步修改。

### 问题 3（轻微，已修复）：同分优先循环为死代码

`header_candidates` 按「分数降序、同分时行号升序」排序后，第一个元素已是最高分且最靠前，原「同分时优先更靠前行」的循环恒不执行。已删除该死循环。

### 问题 4（轻微，已修复）：未使用变量残留

`merging.py` 模板复用路径删除了空行终止逻辑后，`consecutive_empty` 变量不再使用。已删除。

## 五、残余风险

1. 表头识别仍依赖「表头打分最高」这一启发式。三个真实文件已验证成立（表头行打分 0.85+，数据行最高 0.75），但无法对任意格式的文件保证 100%。若未来出现新格式，需要回头补充。
2. 数据采集现为空行完全跳过、仅靠「连续非数据行」终止。若文件末尾存在「数据 + 大量空行 + 无关内容」且无关内容首行恰好形似数据，存在低概率误采。当前目标格式（单一账户明细查询结果）不涉及该场景。
3. `detect_candidate_blocks` 函数及其调用现仅用于填充审计信息 `audit['candidate_blocks']`，无任何消费者，属于可选的后续清理项（不影响正确性，性能开销可忽略）。
